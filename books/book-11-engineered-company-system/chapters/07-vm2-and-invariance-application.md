# 7. VM2 Platform and Invariance Application

## 7.1 Control-plane deployment

The recorded VM2 Compose stack contains `swarm-api`, PostgreSQL 17 and Redis 7, bound
to the Tailscale control-plane address. API migrations run inside the built API image,
not through an operating-system Alembic package. Docker secrets include database,
orchestrator, agent-signing, package-signing, mission-approval and broker material.

## 7.2 Brokered platform operations

The root broker listens on a protected Unix socket. Its worker runs as the dedicated
unprivileged infrastructure identity. Tickets are generated by the control plane,
signed, task/attempt/operation scoped, expiry bounded and single-use. The broker accepts
typed operations, not command strings.

Implemented/rehearsed operation families include Docker/Compose service verification
and controlled restart, service health, Redis, storage, certificates, backups and the
multi-phase Invariance PostgreSQL deployment. A parity rehearsal executed 14 platform
operations, including forced post-check failure and rollback, without touching
production resources; its package remained subject to promotion governance.

## 7.3 Invariance Research database

Historical observed deployment evidence records:

- PostgreSQL 16 and PgBouncer containers on a private data network;
- separate PgBouncer application and worker identities;
- private bindings rather than public PostgreSQL exposure;
- an installed database CA, server certificate and PgBouncer client certificates;
- certificate hostname verification;
- 98 initialized public schema tables;
- a verified pre-schema backup;
- backup configuration and runbook phases.

This database serves the public Invariance Research application, not the Hermes control
plane. Their credentials, schemas, backups and lifecycle are separate.

## 7.4 On-prem application

Historical observed evidence records two private application replicas (`web-a` and
`web-b`) from image `invariance-research-app:4c8874b61f46`, each healthy against
database, schema, runtime and storage checks. Local failover was exercised. Caddy runs
as user `caddy` with only `CAP_NET_BIND_SERVICE`, terminates a Cloudflare Origin
certificate for the Invariance domain and proxies to loopback application ports.

The application environment is root-owned mode `0600`. Google OAuth settings were
moved out of tracked examples. Database traffic uses the private TLS PgBouncer route.
Firewall defaults deny incoming traffic except explicitly allowed SSH/HTTP/HTTPS rules.

## 7.5 Remaining public cutover boundary

Local HTTPS readiness does not prove public reachability. Router forwarding or a
Cloudflare Tunnel, DNS records, Cloudflare SSL mode, external OAuth callback validation,
public smoke tests, fail2ban, monitoring and a tested DNS rollback must be completed and
evidenced before claiming the site publicly deployed. The runbook records progress and
must be resumed through governed operations rather than ad hoc commands.
